# 配置与运行

## 环境和角色

| 项目 | 配置 |
| --- | --- |
| MySQL | `UPGRADE_MYSQL_DSN`，连接使用 UTC、绑定变量和单语句模式 |
| API | `serve -listen 127.0.0.1:8101`，远程访问由 HTTPS 反向代理提供 |
| 验证 | `UPGRADE_DOCKER` 绝对路径与 `UPGRADE_VALIDATION_IMAGE` 的本地镜像 ID |
| 多仓联合演练 | `UPGRADE_REHEARSAL_PROFILE`，默认 `isolated-local`，需与各仓授权匹配 |
| 凭据 | `UPGRADE_WORKSPACE_TOKEN` 只用于客户端。运维可按工作区和操作者撤销 |
| 可选模型 | `UPGRADE_MODEL_URL` 完整路径，`UPGRADE_MODEL_NAME`，可选 `UPGRADE_MODEL_TOKEN` |

令牌范围固定在项目和租户。维护者固定基线和发布计划、发起模型调用。开发者可以审阅补丁、选择命中和记录决定。验证员可以运行测试。管理员可以兼任这些操作。服务通过操作者 ID 记录动作，令牌原文不进数据库。

## 运行中断

每次写入使用 `Idempotency-Key`。相同键和内容返回原回执。复用同键提交新内容会返回冲突。候选和验证任务开始前先写入任务号。客户端失联时可调用 `GET /api/v1/jobs/{id}` 查询，直到任务完成或显示中断。中断保留到期记录和已保留的推理预算，由操作者决定是否发起新任务。

审阅者和维护者可以在候选详情逐项设置审阅决定，再加入同一选集。保存选集时固定工作区基线修订、处理顺序和理由，最多 20 项。执行前可用原请求标识重开选集。每一项的结果和审计记录与该项决定一起提交，失联后重新执行同一批次会从未处理项继续。重新连接同一操作者可从最近 25 个批次中找回原选集，也可以按请求标识直接查询。

| 批量审阅接口 | 行为 |
| --- | --- |
| `POST /api/v1/review-batches` | 使用请求头 `Idempotency-Key` 和请求体 `revision`、`items` 保存选集。每项填写单条审阅所需字段及 `candidate`。 |
| `GET /api/v1/review-batches` | 按创建时间和请求标识倒序返回当前操作者的最近批次标识。 |
| `GET /api/v1/review-batches/{request}` | 读取固定选集及逐项状态，包含审阅回执或拒绝原因。 |
| `POST /api/v1/review-batches/{request}/run` | 按顺序执行未处理项。基线修订变化后，旧批次剩余项会拒绝并保留现场。 |

基线更新清除当前选集。旧补丁和测试仍可供审阅。即使仓库回到同一份文件摘要，也要在新修订重新验证。发起人领到的凭据撤销后，服务拒绝新的写入操作。

上传新基线先调用 `POST /api/v1/snapshots/preview`。预览返回文件差异和当前基线修订。确认时向 `POST /api/v1/snapshots` 传入 `expected_baseline` 和 `expected_revision`。遇到 409 时按新基线重新预览。计划中的源位置可以用 `GET /api/v1/plans/{plan}/source` 查看，传入该计划已经标注的 `path` 与 `line`。

计划列表按当前仓库工作区和精确目标约束查找。示例为 `GET /api/v1/plans?package=laravel%2Fframework&version=%5E13.0`。用回执的 `next` 作为下一页的 `after`；切换仓库需切换工作区凭据。验证报告按计划任务标识对照同批次的基线和候选，并为每个观察保留耗时、状态与输出摘要。

## 验证隔离

验证只运行计划中的 `composer-lock`、`php-lint`、`php-test`。PHP 测试文件必须存在于快照允许范围内。将仓库测试授权给独立验证镜像，镜像应由环境管理员构建并维护。容器用非 root UID、只读挂载、无网络、无额外权限、1 CPU、256 MiB 存储器限制与临时目录运行。输出在读取上限内计算摘要，运行日志保留耗时、退出码与观察状态。

Composer 查询还有平台、替换包、插件和外部仓库语义。内建解析器的候选只代表在给定目录中找到解。最终验证使用实际 Composer，遇到不支持的版本表达式或缺少平台信息时记录待复核。

含 `composer.lock` 的 PHP 测试先在容器临时目录按锁安装依赖，再运行批准的 PHP 文件。依赖安装失败时验证显示不可用。外部依赖由运维在受控准备环境预缓存，放入镜像内只读的 `/opt/upgrade-agent/composer-cache`。生产验证容器保持无网络，输入挂载保持只读，并禁用 Composer 脚本和插件。依赖规模需适配容器时限与 64 MiB 临时目录。 [Laravel 准备步骤](../examples/laravel-pricing/MIGRATION.md)

多仓矩阵每个组合限时 120 秒，1 CPU、640 MiB 内存和 384 MiB 临时工作盘。测试只使用该容器内回环服务。工作进程重启后继续处理排队任务，4 分钟的租约到期后可重新认领未完成组合。对于依赖缺失，保留失败回执，可在同一快照组合上重新验证；生产应把批准的 PHP 依赖和固定运行镜像一起准备。 [矩阵与交付操作](contract-estate.md)

## 模型与预算

只允许管理员配置 HTTPS 服务或字面回环地址的 HTTP 服务，模型连接不走环境代理或重定向。应用根据获批片段的字节数保守预留预算，收到服务计量后更新实际 token 数。缺失计量保留预留值，费用需要结合服务方费率。回放只用于演示，记录标为 `replay`。

## 备份与恢复

用及时备份保留工作区、快照、计划、证据、审阅和任务回执。数据库凭据与模型配置由部署环境管理。MySQL 包含二进制凭据摘要，备份要使用 `mysqldump --single-transaction --hex-blob`。恢复到独立数据库后，用原有工作区令牌检查历史批次、验证记录和导出摘要。迁移 3 增加批量审阅表，迁移 4 为已有计划回填目标索引。升级后检查服务就绪端点，再用旧凭据读取已有计划与报告，验证目标查询。 [升级与恢复记录](results/upgrade-rehearsal.json)

迁移 5 添加仓群与活动对象。升级前应备份现有数据库并在副本核对原计划、补丁及报告；部署后验证仓库权限、旧计划导入和矩阵队列。回退前停收活动、导出未交付清单并保存 Git 实际采纳回执。恢复存档时使用单独库，逐项对照过去的采纳提交，防止重复应用。 [2.0 实测恢复](results/contract-upgrade-v2.json)

## 数据保留

运维可以使用 `upgrade-agent prune -tenant workshop -workspace pricing -before 2026-01-01T00:00:00Z` 预览该工作区的到期记录。完成备份后，用同样的范围和日期增加 `-apply` 执行清理。每次最多处理 250 个审计事件、250 个无有效引用的快照。当前基线、有计划引用的历史快照和任务回执继续保留。工具记录实际清理数量，可重复执行直到本期限内没有候选。
